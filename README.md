# Spool API

Backend for **Spool**, *a place for your loose threads*: a companion app for people in therapy. It covers the thought journal, recorded sessions with AI summaries, goals, appointments and meditations.

Built with NestJS 12, TypeORM and PostgreSQL. Session summaries are generated by Claude (`claude-opus-5-5`). The mobile client lives in [spool-mob](https://github.com/jkhandeveloper/spool-mob).

## Quick start

```bash
cp .env.example .env          # then edit secrets / ANTHROPIC_API_KEY
docker compose up -d db       # Postgres on :5432 (also creates spool_test)
npm install
npm run start:dev             # http://localhost:3000/api/v1
```

Migrations run automatically on startup (`migrationsRun`) unless `DB_SYNCHRONIZE=true`.

| Script | What it does |
|---|---|
| `npm run start:dev` | Watch mode |
| `npm run build && npm run start:prod` | Production build |
| `npm test` | Unit tests (Vitest) |
| `npm run test:e2e` | End-to-end tests against Postgres |
| `npm run lint` / `npm run typecheck` | oxlint / tsc |
| `npm run migration:generate -- src/database/migrations/Name` | Generate a migration from entity changes, then add it to `src/database/migrations/index.ts` |
| `npm run migration:run` / `migration:revert` | Apply / roll back migrations |

### Running the tests

The e2e suite needs a Postgres database and defaults to
`postgres://spool:spool@localhost:55432/spool_test`. With the compose file above, run:

```bash
DATABASE_URL=postgres://spool:spool@localhost:5432/spool_test npm run test:e2e
```

The suite truncates every table in that database before it runs, and it uses the offline `local` summarizer, so it never calls Claude.

## Configuration

See [.env.example](.env.example). Key settings:

- `DATABASE_URL`: Postgres connection string.
- `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`: required in production.
- `SUMMARY_PROVIDER`: `anthropic` (default) or `local`, an offline heuristic for dev and tests only.
- `ANTHROPIC_API_KEY`: credentials for Claude. The SDK also picks up `ant auth login` profiles.
- `ANTHROPIC_MODEL`: defaults to `claude-opus-5-5`.
- `TRUST_PROXY`: number of reverse proxies in front of the API (set to `1` behind nginx), so rate limits use the real client IP.

## Privacy model

These are the promises the consent script (screen 02) makes, and how the API keeps them:

- **Audio never reaches the server.** The app transcribes on the device, and only text is uploaded.
- **The transcript is deleted once the summary draft is created.** It sits in a `select: false` column and is never serialized (`@Exclude`). It's erased when the session becomes a `draft`, or when a failure can't be retried. A retryable failure keeps it so that **Try again** works. Discarding the session deletes it.
- **The user reviews every summary before it's saved** (screen 12). Saving with "Keep this summary" unchecked keeps the goals and deletes the summary itself.
- Users can export everything (`GET /me/export`), delete all data but keep the account (`DELETE /me/data`), or delete the account (`POST /me/delete-account`, which asks for the password). Every owned row cascades.
- In journal-only mode (`journalOnly`), the server refuses to create sessions.

Claude is the only outside processor. It receives the transcript text and the discussion prompts. Its system prompt tells it to treat the transcript as material to summarize, not as instructions. Requests set `fallbacks: "default"`, so a safety decline is retried on a fallback model. If the whole chain refuses, the session fails without a retry and the transcript is dropped.

## API overview

All routes are under `/api/v1`. Every route needs a `Bearer` access token except `auth/*` (other than `logout`) and `health`.

| Area | Endpoints |
|---|---|
| Auth (P1) | `POST auth/register`, `auth/login`, `auth/refresh`, `auth/logout`, `auth/forgot-password`, `auth/reset-password` |
| Me / settings (P2, P9) | `GET/PATCH me`, `POST me/privacy-review`, `POST/DELETE me/graduate`, `GET me/export`, `DELETE me/data`, `POST me/delete-account` |
| Today (01) | `GET today?hour=<local hour>`: reminder, meditation, next appointment, goals, pending session |
| Journal (06, 07, P6) | `GET/POST journal`, `GET/PATCH/DELETE journal/:id` (`includeInPrompts` controls prompt use) |
| Sessions (02–04, 11, 12, P5) | `GET sessions` (history), `GET sessions/pending`, `GET sessions/prompts`, `POST sessions`, `GET sessions/:id`, `POST sessions/:id/transcript`, `POST sessions/:id/retry`, `PATCH sessions/:id`, `POST sessions/:id/save`, `DELETE sessions/:id` |
| Goals (P4) | `GET/POST goals`, `GET/PATCH goals/:id`, `POST goals/:id/check-ins` |
| Appointments (05, 10, P7) | `GET appointments?from&to`, `GET appointments/next`, `POST appointments`, `GET/PATCH/DELETE appointments/:id` (delete cancels) |
| Meditations (P3) | `GET meditations`, `GET meditations/:id` |
| Health | `GET health` |

### Session lifecycle

```
POST /sessions {consentConfirmed: true, prompts}        -> recording
POST /sessions/:id/transcript {transcript, durationSeconds}
                                                         -> processing (202; summarizing runs in the background)
GET  /sessions/:id  (poll)                               -> draft | failed {failureReason, canRetry}
POST /sessions/:id/retry                                 -> processing
PATCH /sessions/:id {mainPoints, takeaways, dailyGoal…}  (review/edit)
POST /sessions/:id/save {keep}                           -> saved (goals become active)
DELETE /sessions/:id                                     (discard)
```

If a session is still `processing` after 5 minutes (for example, the server restarted), it's marked `failed` with `canRetry: true`.

Discussion prompts (`GET sessions/prompts`) come from journal entries written since the last saved session, going back at most 14 days, that have `includeInPrompts: true`.

## Known gaps / next steps

- **Password reset email.** No mail provider is wired up yet. The reset token goes to the server log, and outside production it's also returned as `devResetToken` so the app flow can be tested.
- **Reminders.** Reminder preferences are stored, but no push notifications are sent from the server yet. The mobile app schedules local notifications.
- **Background summarizing runs in the API process.** To scale past one instance, move it to a queue (for example BullMQ).
- Open product decisions from the wireflow are still unsettled: therapist collaboration, sharing, and subscription. The current design is client-only, with no sharing, and free.
